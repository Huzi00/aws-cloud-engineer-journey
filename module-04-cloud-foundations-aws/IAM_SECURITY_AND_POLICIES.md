# AWS IAM Architecture & Security Policy Mechanics

## Core IAM Components
- **IAM Users:** Persistent identity assigned to a person or legacy system (requires login credentials/access keys).
- **IAM Groups:** Collections of Users used to apply uniform permission sets at scale.
- **IAM Roles:** Temporary identity assumed by trusted entities (EC2 instances, Lambda functions, cross-account users) using temporary credentials generated by AWS STS (Security Token Service).
- **IAM Policies:** JSON documents defining explicit permissions attached to Users, Groups, or Roles.

## Policy Evaluation Logic
1. **Explicit Deny Always Wins:** If an explicit `Deny` matches an action, the request is denied regardless of any `Allow` statements.
2. **Default Deny:** All requests are implicitly denied unless explicitly allowed by a policy.
3. **Explicit Allow:** Action is granted only if an `Allow` statement matches and no explicit `Deny` exists.

## Principle of Least Privilege (PoLP)
Granting entities *only* the minimum permissions necessary to perform their required job functions, for the minimum required duration.

## AWS IAM Security Best Practices
- Root Account: Secure with hardware/virtual MFA and lock away root access keys.
- Prefer **Roles over Users** for application workloads (e.g., attaching an IAM Role to an EC2 instance instead of embedding hardcoded static Access Keys).
